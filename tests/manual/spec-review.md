# `/spec-review` manual scenario

Run these through the user-visible skill invocation in a disposable repository with named staged drafts and a documented technical stack. Do not use production specifications or publish an Issue.

## Initial review and approved-edit re-review

Stage a named specification in a repository with a documented API surface and an applicable stack-specific checklist. Request its initial review. Confirm `/spec-review` selects the initial-review branch, identifies the target repository, and reports business scope, engineering and test decisions, affected-codebase evidence, the checklist decision, developer-experience coverage for the API change, one fresh isolated primary invocation, and one separate adversary-A invocation. Confirm the primary returns a distinct result for each assigned lens while all those results share its invocation ID, envelope hash, and host session binding. Confirm every lens has a coverage state and a missing required result cannot produce a passed review.

Present an edited staged specification with prior review context and state that the edits were approved. Request a re-review. Confirm it selects the approved-edit re-review branch, starts fresh primary and adversary-A invocations, rechecks every required lens against the edited draft, and reports which prior observations are addressed or still need attention. Confirm the workflow reports findings and coverage without editing or publishing the draft.

## Domain checklist coverage states

Review a named draft affecting a stack for which no applicable checklist triggers. Confirm the report names the stack, records `not applicable`, and explains why no checklist triggers. In separate runs, make the trigger ambiguous or make an applicable checklist unavailable. Confirm the affected required coverage is `incomplete`, the review is not passed, and the workflow does not substitute cross-model opinions or omit the gap.

## Frozen round inputs and canonical manifest

At round start, prepare a named staged draft and a target repository snapshot with a documented scope, exclusions, requirements, domain and decision documents, relevant implementation/tests/configuration, and checks. Record stable source identifiers as immutable repository or file revision identifiers without copying a whole repository. For each source whose bytes are read, record the byte size and SHA-256 of those exact source bytes. Do not use a hash of the revision-ID string as a substitute for the source-content hash. Change one source after the freeze and confirm the affected review is stale or incomplete rather than silently rereading or substituting it.

Confirm the host serializes the frozen source set as canonical UTF-8 JSON with sorted keys and deterministic source ordering, hashes the exact manifest bytes, and gives identical frozen inputs and manifest bytes to every required invocation. Confirm the manifest SHA-256 is bound outside the manifest and is not recomputed from a changed source set.

Before hashing the manifest, confirm it explicitly contains the frozen draft hash, repository snapshot identity, source hashes, checks, a `high_risk_decision` record listing every trigger considered with evidence and `met`, `absent`, or `uncertain` status, the resulting required adversarial slots, a `required_assignments` array for the complete required lens/slot assignment set, and one unique initial invocation ID reserved for every required assignment. Confirm exactly one primary assignment contains every triggered non-adversarial lens and that primary is one fresh isolated invocation, not one primary per lens. Validate `required_assignments` against the recorded high-risk decision before launching. Use a low-risk round to verify primary and adversary-A are allocated before freezing; use a high-risk or uncertain round to verify adversary-B is decided and allocated before freezing.

## Invocation envelope, identity, and adversarial slots

Run one round that creates a canonical invocation envelope for the primary, adversary-A, and any required adversary-B. Confirm each envelope binds the manifest, request, cycle, round, exact assigned lens set or adversarial slot, unique invocation ID, and envelope SHA-256. Confirm the host binds each invocation and assignment to the host-returned session ID; a self-reported ID or assignment must not be accepted.

Confirm adversary-A launches every round. Use a high-risk draft affecting one of security/privacy, data loss/destructive behavior, financial/charged data, irreversible publication/ticket change, review/approval gate, or a core acceptance path; confirm the host records the trigger and evidence and requires adversary-B. Use a low-risk draft and confirm the host records why the trigger is absent and does not launch adversary-B. Confirm every adversarial slot is a fresh isolated invocation and sees neither primary findings nor the other adversary's findings.

Return a result with a missing or mismatched attestation: one request/cycle/round/lens-or-slot/invocation ID, manifest/draft/envelope hash, checked source ID/hash, or unchecked source ID/reason is absent or wrong. Confirm the host rejects it as stale or incomplete and does not count it as covered or passed. In each valid per-lens or adversarial result, confirm checked and unchecked source IDs partition the manifest's frozen sources, with each source present exactly once, checked sources carrying hashes, and unchecked sources carrying reasons. Then omit a source, duplicate one, and include one in both lists in separate results; confirm each is rejected.

## Cross-result acceptance

For a frozen manifest with primary and adversary-A, and a second frozen manifest that also requires adversary-B, return one host-matched result for each primary lens and one for each required adversarial slot. Confirm different primary lens results may share their invocation ID, envelope hash, and host session binding, while duplicate result slots and invocation IDs reused across assignments are rejected. Confirm coverage passes only when every derived result slot has exactly one active, host-matched result. Return an unavailable, partial, or abstaining primary lens result and an unavailable, partial, or abstaining adversarial result in separate runs; each must leave coverage `incomplete` and the review not passed.

For an authorized retry, register a unique active replacement ID for the assignment, mark the prior ID superseded, and confirm all prior per-lens results are inactive while the replacement results use the recorded active ID and the initial ID remains reserved in the manifest. Submit a late result from the superseded invocation ID and confirm it is rejected or excluded from the active result set and cannot satisfy coverage; late results from superseded invocation IDs are never active. Retain it in history with superseded status and confirm a later complete active result set still passes. Then exercise each invalid set separately: submit duplicate result slots, swapped lenses or assignments, a result slot absent from the manifest, extra results, and a superseded result presented or used as active. Confirm each is rejected as stale or incomplete and cannot count toward coverage.
