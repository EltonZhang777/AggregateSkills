# Child-session initial prompt template

## Fill instructions

Create one prompt for each explicitly approved group. Replace every bracketed placeholder with confirmed, group-specific information before using the template for handoff; do not leave unresolved placeholders. Use only confirmed information and do not invent missing facts. Exclude sibling requirements and unrelated parent history. Include only the global rules, dependencies, repository context, and write constraints that apply to this group. Do not include a full worked example.

For dependencies, name known blockers and their current state; say `None` only when the parent has confirmed there are none. For write constraints, carry forward the applicable shared-workspace and authorization rules without broadening them. For project text, include the normative language rule from the target repository's root `AGENTS.md`; if the target is another repository, the parent must read that repository's root file before drafting.

### Spec review and publication

If `/to-spec` can reliably stop before creating or publishing an Issue, use it for seam confirmation and drafting, then stop before publication. If it cannot reliably stop, use its seam criteria and draft template without invoking its publishing step. After seam confirmation, show the exact draft text and a unique temporary path; obtain explicit approval of that text and authorization for the path, then stage with create-new semantics and verify the frozen bytes and SHA-256.

Run `/spec-review` on the staged bytes before any Issue publication. Apply no candidate without approval of the exact batch, source version, and destination plus write authorization. Review approved edits in a fresh round of the same named cycle, with at most three numbered rounds per cycle. An unresolved cycle limit requires asking whether the user authorizes another named cycle or wants another action.

Preview the exact Issue title and body, canonical owner/repository target, required labels, and exact UTF-8 body SHA-256. The Issue body bytes must equal the reviewed draft bytes. Obtain final specification approval and publication authorization separately, each bound to title, draft SHA-256, canonical owner/repository, and required labels. Publish only while both approvals are recorded and still match the tuple. A body-byte change requires fresh review and new approvals; any title, target, or required-label change invalidates both approvals and requires a new preview and both approvals. A review pass or candidate approval is not final approval.

After spec publication and all required labels are reconciled, obtain the user's explicit authorization for ticket reconciliation. Do not invoke `/to-tickets` before review coverage, both exact final approvals, and successful spec publication. Before invoking it, re-read its live instructions and prove it can return the ticket plan and reliably stop before any Issue write. If it can, use it only to prepare the plan and stop before its first write. If it cannot, do not invoke its publishing step; use its existing criteria and template to prepare and freeze the exact ticket set in task progress without publishing. Present each title, body, canonical target, required labels, and blocking edges.

Before every GitHub list, read, create, edit, label, or link operation, explicitly select the canonical owner/repository. Pass `--repo <owner>/<repo>` to every `gh` command that supports it, and use an explicit `repos/<owner>/<repo>/...` path for every `gh api` endpoint. Never rely on `gh`'s configured default repository. Immediately before and after each write, verify every involved Issue belongs to that canonical repository; stop before writing if the target or repository cannot be established.

Before every GitHub Issue create/edit, label create/change, or link write, obtain and verify an atomic exclusive writer claim keyed by canonical owner/repository and the exact approved publication tuple, ticket payload, or ticket graph/link delta. Record the claim owner's host/session ID, unique operation ID, exact key, and attempt state in task progress before writing. No second session writes while a claim or operation is active or unresolved. Release only after terminal read-back reconciliation; take over only after the previous owner stopped and all its operations were reconciled. A progress note alone is not an atomic claim; stop if the host cannot verify the claim.

Before every ticket create, edit, label change, or link, re-read the parent spec Issue using its exact approved Issue ID. Verify the returned ID, approved title, canonical owner/repository, exact approved body bytes and their SHA-256, that every approved required label is present, and that the current required-label tuple matches the approved tuple. If any differs, stop and invalidate both final spec approvals, publication authorization, ticket-set approval, separate Issue-creation authorization, every affected ticket-payload or graph/link-delta approval, and any independent link-write authorization before any ticket write continues. If the exact body bytes are not byte-identical or the SHA-256 differs, freeze the newly read body and run a fresh `/spec-review` round. Require that round to pass before re-previewing or requesting, binding, or recording any replacement approval or write authorization; no replacement approval or write authorization may exist before that pass. Only after the new review passes, re-preview the exact publication tuple, affected ticket proposal, and exact edges plus canonical target; obtain fresh applicable final spec approvals, publication authorization, ticket-set approval, separate Issue-creation authorization, affected ticket-payload or graph/link-delta approvals, and explicit link authorization bound to the parent Issue ID, body hash, canonical target, and exact graph as applicable. If body bytes and SHA-256 remain identical but only the parent Issue ID, title, canonical owner/repository, or required-label presence/tuple differs, re-preview the exact affected publication tuple and ticket proposals/edges. Re-obtain every invalidated applicable approval and authorization: final specification approval, publication authorization, ticket-set approval, separate Issue-creation authorization, affected ticket-payload or graph/link-delta approval, and any applicable independent write authorization, including explicit link-write authorization for affected graph changes; bind each to the updated parent tuple and exact payload/graph delta. Restore or reconfirm successful publication against that tuple, with all required labels verified by read-back, before resuming ticket writes. Metadata-only drift does not require or imply a new `/spec-review` round solely because of that drift. No ticket write may proceed until applicable approvals are fresh and successful publication is reconfirmed. Immediately before and after each write, verify the repository of every involved Issue. Before an existing-ticket field or edge update, issue one field or edge write at a time; record a unique operation ID and cumulative attempt state, then compare the immediate pre-read state with the exact approved baseline or last verified state and expected state. Drift requires a newly approved exact delta. Read back each write and verify its exact result before advancing. Reconcile an ambiguous response before retrying; retry only a clearly transient failure when read-back confirms that exact write is missing, at most three attempts per write across resumes. Missing or conflicting history stops without retry.

Before each Issue create, record a unique operation ID and cumulative attempt state and verify the target immediately before writing; keep at most one unresolved operation per key. After an ambiguous result, fully paginate Issues in all states, exclude pull requests, and read back candidates. Accept only one exact target/title/body match. Stop on incomplete enumeration, multiple or mismatched results, or unknown outcomes. Retry only a confirmed transient failure after a complete listing proves no Issue was created, at most three attempts across resumes. After Issue read-back, create and verify required labels, then apply them with `ready-for-agent` last. Verify the Issue's canonical repository before each label write. Record per-label operation and attempt state before writing; reconcile ambiguous responses by read-back and retry only confirmed transient failures, at most three attempts per label. Spec publication succeeds only after the Issue and all required labels are verified by read-back.

### Native ticket linking

Reconcile existing tickets by exact known Issue IDs. Read each title, body, state, labels, parent, and blocking edges. Present tickets as unchanged, revised, superseded, or new, with exact proposed field and edge changes. Do not duplicate tickets, infer closures, or change a link from a title match. Obtain exact ticket-set approval, then separately obtain explicit Issue-creation authorization; bind both records to the parent spec Issue ID, its exact approved body SHA-256, canonical owner/repository target, and exact ticket payload plus graph. On the safe `/to-tickets` path, its publication confirmation serves as the separate Issue-creation authorization and must bind to that tuple; in the template fallback, obtain the explicit authorization directly. Before any native link write, present the exact proposed edges and canonical target and obtain separate explicit link authorization, distinct from ticket-set approval and Issue-creation authorization. Bind it to the parent spec Issue ID, exact approved body SHA-256, canonical target, and exact graph. Issue-creation authorization never permits links; if only it exists, do not link. Obtain separate approval for each later ticket-payload or graph/link delta and bind it to the same parent ID, hash, and target plus the exact delta. Ticket-set approval alone authorizes no write: create only after separate Issue-creation authorization, update only after exact payload-delta approval, and link only after exact graph/link approval and link authorization. Each write also requires its writer claim and applicable publication or relationship gate. Approval of a planned ticket set alone authorizes no Issue creation, edit, label change, or link.

After all planned tickets exist, the exact graph and separate link authorization are approved, and the existing seam, ticket-granularity, blocking-edge, and publication gates pass, confirm the configured tracker is GitHub and that native sub-issues and the required permissions are available. If GitHub, native sub-issues, or required permissions are unavailable, report the blocker and stop. Add only links in the explicitly approved graph; Issue-creation authorization alone never permits a link.

Before each link, confirm the ticket exists, read its current parent, and fully paginate the spec's sub-issues. Treat a link as already complete only when both reads confirm the same spec parent; skip that write. Treat a 404 from the parent endpoint as no parent only after the ticket exists and the spec's complete sub-issues read succeeds and the list does not contain the ticket; any other read error leaves the relationship unknown. Immediately before adding a missing link with `gh issue edit <spec-number> --add-sub-issue <ticket-number> --repo <owner>/<repo>`, re-read the parent spec Issue and the ticket, verify both repositories, compare the state to the approved graph, record the operation ID and attempt state, and obtain the atomic writer claim for the exact approved graph/link delta. Read both Issues and relationships back immediately afterward before advancing.

If the ticket has a different parent, the reads disagree, or the current state cannot be established, pause and ask the user; never reparent automatically. After a failed or ambiguous write, reread both relationships. If the intended parent is now confirmed, mark that link complete. Otherwise retry only the still-missing link after another successful read, and only for a clearly transient failure, with at most three total write attempts per link, including the first. Record the cumulative attempt count in the child progress summary before each write and update it before every retry; carry it across resume. If the prior count is missing or incomplete, stop instead of retrying automatically. Stop on other errors or when the limit is reached, and report links that succeeded or remain pending.

Preserve ticket and spec issue titles, bodies, labels, states, and blocker edges: before linking, record these fields; after linking, verify them. Then verify every link by rereading each ticket's native parent relationship and fully paginating the spec's sub-issues list to confirm all planned tickets appear. Leave the spec issue's state unchanged.

Use the target repository's root `AGENTS.md` language rule for new or materially rewritten project text, and pass that rule to `/grill-duo-with-docs`, `/to-spec`, `/spec-review`, `/to-tickets`, and `/conventional-git-messages` when used. If the target repository differs from the source repository, read its root `AGENTS.md` before drafting; do not substitute the source or skill-installation rule. Preserve untouched text and pause if the target rule has no discernible dominant language.

Before `/to-spec` or `/to-tickets` drafts a GitHub issue title or body, re-read the original `/conventional-git-messages` `SKILL.md` and invoke it with the known facts and target repository language rule. Follow the approved group's shared workspace and write-authorization rules; stop for user input whenever a required decision or authorization is missing.

### Optional document integration follow-up

For a local-artifact group, offer this follow-up only for the group's approved generated document set; do not include the workflow's own skill, tests, manuals, or other implementation files. After task-branch publication and applicable issue/status checkpoints, provide a summary naming the task branch, exact document paths, and proposed destination branch before asking whether the user wants to start the integration. State that accepting will create one focused local commit containing only those documents on the destination branch. Use only a destination established by user-confirmed context or repository guidance; if it is unclear, ask the user to name it and pause without integrating.

An affirmative response authorizes only that focused local commit of the listed documents on the named destination branch and does not extend the task-branch grant in ADR-0003. Continue with the same host agent in the same conversation; do not create a new conversation or subagent. Stop if the destination is unclear, unrelated changes are present, or conflicts occur; do not overwrite destination work or include unrelated changes.

Declining or giving no clear authorization leaves the documents on the task branch and the destination unchanged. Pushing the destination branch still requires the separate explicit confirmation from the existing grilling step.
