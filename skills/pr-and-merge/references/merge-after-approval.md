# Merge after approval

Merge each PR only after the user explicitly approves that exact PR. For a multi-PR batch, retain the batch-plan order through merging: among dependency-ready entries, process conflict-free entries before conflict candidates, using the supplied or original input order only to break ties within either group. Immediately before each merge, recheck that PR's head and base, mergeability, required checks, and repository merge policy. A blocker stops that PR and its dependents; continue with other approved independent PRs. Also confirm the supplied worktree is clean; if it became dirty, stop and ask:

```sh
gh pr view NUMBER --repo OWNER/REPO --json state,isDraft,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup,headRefName,headRefOid,baseRefName,baseRefOid,url
gh pr checks NUMBER --repo OWNER/REPO
```

A failed, pending, or unknown required check, an unmergeable PR, or an unclear policy blocks that PR. For a single-PR approval, if either OID differs from the reviewed PR, refresh the diff and checks and get renewed approval. For a batch authorization, follow [the multi-PR refresh rule](multi-pr-batch.md#refresh-after-source-or-base-changes): a base OID advancement alone does not revoke authorization when the approved source head and target base ref are unchanged and no new conflict-resolution work is required; refresh the diff and live checks. After an upstream PR merges, retarget each directly stacked downstream PR to the upstream PR's former base with gh pr edit NUMBER --repo OWNER/REPO --base TARGET_BASE. Re-read its head and base OIDs, diff, required checks, and mergeability. Get renewed explicit approval if retargeting materially changes the diff, invalidates the prior approval, or changes either OID. A retargeting or check failure blocks that PR and its dependents only. Follow the repository's explicitly documented merge method. If the policy does not select an enabled method, ask which enabled method to use; if none is enabled, block the merge. Do not infer a method from the available options alone. Merge with exactly one of `gh pr merge NUMBER --merge`, `gh pr merge NUMBER --squash`, or `gh pr merge NUMBER --rebase`, as the policy requires. Do not use auto-merge.

After all of those live gates pass, and immediately before invoking `gh pr merge`, check the current GitHub CLI identity's effective permission on the exact repository that owns the PR's base branch. This is an additional gate; preserve the explicit approval, head and base OID, mergeability, review, required-check, repository-policy, and merge-method gates above. The PR API is authoritative for the base repository because `gh pr view --json` does not expose `baseRepository`:

```sh
gh api --include repos/OWNER/REPO/pulls/NUMBER
gh api --include user
gh api --include repos/BASE_OWNER/BASE_REPO/collaborators/USERNAME/permission
```

Read `.base.repo.full_name` and `.login` from the first two JSON bodies, then use them as the `BASE_OWNER/BASE_REPO` and `USERNAME` in the permission request; do not substitute the source repository, local remote, or a guessed login. With `--include`, retain the HTTP status, rate-limit headers, and JSON body from all three calls; use each body only for its JSON fields. Normalize the response case-insensitively. A recognized `permission=admin`, `write`, or `read` establishes ADMIN, WRITE, or READ even when `role_name` is a custom value. `role_name=maintain` distinguishes MAINTAIN from legacy `permission=write`, and `role_name=triage` distinguishes TRIAGE from legacy `permission=read`; matching base role names are also recognized. If recognized fields conflict (for example, `permission=read` with `role_name=maintain`), the result is inconclusive. Missing `permission` evidence, `permission=none`, or an unrecognized `permission` value is inconclusive even if `role_name` is present; an unrecognized value in both fields or otherwise empty, unavailable, malformed, custom-only, or unmappable evidence is also inconclusive. HTTP 404 is inconclusive. Inconclusive evidence never establishes denial or permission. A known ADMIN, WRITE, or MAINTAIN result is positive and permits the merge gate to continue. A known READ or TRIAGE result is a definite denial: report it and never invoke `gh pr merge`.

Count each started permission lookup sequence (base repository, identity, and permission response) as one check, even when it fails partway through. A valid permission result that maps to READ or TRIAGE is a definite denial: report it and block the entry immediately without another check or retry prompt, regardless of the remaining retry budget. A permission lookup that returns HTTP 404, or completes with empty, malformed, missing, conflicting, or unmappable base-repository, identity, or permission evidence (including permission=none), is inconclusive: report it and pause immediately to ask whether to retry or skip; do not automatically retry inconclusive results. Automatically retry only recognizable transient failures, such as a transport timeout/reset, HTTP 408/429/500/502/503/504, or an explicit primary or secondary rate-limit response, with at most three started checks in one automatic cycle; waiting for a retry time consumes no attempt. Treat authentication, configuration, and other unexplained access failures as a pause: report the evidence and ask whether to retry or skip. A user-selected retry after a pause permits exactly one extra check and does not silently reset the automatic budget. When an automatic cycle consumes three checks on recognizable transient failures without a positive result or a known denial, pause and ask whether to authorize exactly one additional check or skip. After any user-selected check, a known READ or TRIAGE is still an immediate denial. If its result is inconclusive or another retryable/access failure occurs, pause again and ask whether to retry or skip; each new user-selected retry authorizes exactly one additional check. Skipping blocks the entry. Only a positive result allows the workflow to continue toward merging.

For a rate-limit response, honor `Retry-After` when present. Otherwise, when `x-ratelimit-remaining=0`, wait until `x-ratelimit-reset`; for a secondary limit without either header, wait at least one minute, increasing the backoff if the limit recurs. Auto-wait when the safe delay is at most five minutes. For a longer delay, pause and report the earliest safe retry time; do not issue a check or merge before it. A wait never authorizes another check by itself. After an auto-wait, start another automatic check only if fewer than three checks have started in that cycle; if the budget is exhausted, pause and ask whether to authorize exactly one additional check or skip. If a user-authorized check hits a rate limit, honor the safe delay and pause again; after that delay, ask for a fresh one-check authorization before another permission attempt. After any wait or when resuming a paused check, refresh every existing pre-merge gate before another permission attempt: confirm explicit approval and its snapshot, head and base OIDs, mergeability, reviews, required checks, repository policy, and merge method. If an OID or approval snapshot changed, follow the existing refresh and renewed-approval rules above and in [the multi-PR refresh rule](multi-pr-batch.md#refresh-after-source-or-base-changes). Then query permission again as the final gate immediately before `gh pr merge`; do not perform another wait or unrelated gate between a positive permission result and the merge command. In a batch, a denied, inconclusive, exhausted, or paused permission gate blocks that entry and its dependents, while unrelated eligible entries continue. Never invoke `gh pr merge` for a denied or inconclusive result.

After the command succeeds, verify the PR result:

```sh
gh pr view NUMBER --repo OWNER/REPO --json state,mergedAt,url
```

Confirm `state` is `MERGED` and `mergedAt` is set before reporting success. Otherwise report the observed state and stop.

When an approved merge encounters a conflict, use `/resolving-merge-conflicts`, but stop before its commit step. Run required local checks on the resolved worktree and inspect its status and complete unstaged diff. If any changed path is outside the conflict resolution, stop. Present the exact diff, check results, and intended commit, push, and merge, then get explicit approval for that diff and write set before staging or any other write. After approval, stage only the approved files and inspect the staged diff. If it differs from the approved diff, stop and get renewed approval before any commit, push, or merge. After the push, confirm the PR diff still matches the approved resolution and record its head and base OIDs. Recheck PR checks and mergeability before merging; any later OID or diff change requires renewed approval.

Never merge a PR outside the supplied batch, post PR comments, or delete branches or worktrees as part of this workflow.
