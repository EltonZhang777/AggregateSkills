本指南用于端到端检查 `/pr-and-merge` 的单 PR 与多 PR 批次创建、复用、检查和合并审批流程。标准手测使用隔离的 GitHub 仓库；本次 #42 按用户指示在当前仓库执行，所有测试 PR 只允许以 `codex/issue-40-pr-and-merge` 为目标分支，不能使用默认分支。详细场景及预期结果见 [`tests/manual/pr-and-merge.md`](../../tests/manual/pr-and-merge.md)。

本次 #42 手测已通过批次排序、脏项隔离、堆叠 PR 重定向及再次审批：PR #57 合并后，PR #58 重定向到 #57 原目标分支，重新检查差异、检查状态和可合并性，并在再次批准后完成合并。该测试使用同一仓库，未使用隔离仓库。Issue #40 于 2026-10-01 续测：失败门禁与实时门禁翻转已验证；隔离仓库覆盖按用户指示跳过；周期依赖场景作规则推演；冲突修复已提交并推送验证，PR #62 未合并。

## 准备

1. 本次 #42 按用户指示在当前 AggregateSkills 仓库执行；将 `codex/issue-40-pr-and-merge` 作为专用测试目标，只创建可丢弃的 codex 测试分支，不操作默认分支。记录这是非隔离仓库测试。
2. 按 [`docs/prerequisites.md`](../prerequisites.md) 安装并检查 `gh`、`/conventional-git-messages` 和 `/resolving-merge-conflicts`。先运行 `gh auth status` 确认登录的是预期账号。
3. 核对测试目标分支的保护规则、必需状态检查和仓库合并策略。需要测试“未知”或“冲突”策略时，单独准备相应配置。
4. 为批次中的每个源分支准备独立 worktree，并明确标出堆叠依赖。除复用 PR 场景外，每个场景使用新分支；不要让多个测试共享尚未处理的本地改动。脏分支隔离测试要保留一个未提交改动以确认该项和其依赖被阻断。

## 执行步骤

1. 从 Codex 的技能调用入口运行 `/pr-and-merge`，在一次调用中列出每个仓库、源分支或 worktree、目标分支及堆叠关系。独立分支按请求顺序提供。
2. 按场景准备分支状态、已有 PR、检查结果或合并策略，再发起调用。检查每个 PR 有独立审批快照；涉及创建、推送、更新或合并时，只在对应审批点确认。
3. 对照场景清单检查仓库、源分支、目标分支、PR、差异、必需检查和当前提交 OID。确认阻断或信息不明确时，技能没有继续产生外部写入。
4. 合并场景中，先让检查通过并批准指定 PR；再改变检查状态或 PR 的 head/base OID，确认技能重新检查并要求必要的再次批准。
5. 每个场景完成后填写下方记录。若发生未预期的推送、PR 修改或合并，停止后续场景并保留 PR 链接和调用输出供排查。

## 覆盖场景

按 [`tests/manual/pr-and-merge.md`](../../tests/manual/pr-and-merge.md) 逐项执行：

- 干净分支：默认目标与显式非默认目标。
- 已有 PR：复用、仅推送本地新增提交、保留原 base；目标冲突及已关闭 PR。
- 脏工作区、必需预检查失败或不可用、检查产生未跟踪文件。
- 仓库/目标不明确、堆叠分支 base 冲突、合并策略不明确。
- 检查状态变化以及批准后的 head/base OID 变化。
- 冲突解决后的第二次批准、推送后检查和差异核对。
- 多 PR：依赖优先、独立项按输入顺序；堆叠 PR 在上游合并后重定向并重验；脏分支或失败检查只阻断该项及其依赖。
- 非 GitHub 托管平台。
